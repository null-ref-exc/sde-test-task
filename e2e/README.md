# E2E тесты

## Shell

```sh
sh e2e/run-e2e.sh
sh e2e/run-e2e.sh --docker
```

`--skip-build` пропускает сборку; в Docker-режиме должен существовать образ `vulnerability-tracker:e2e`. `PYTHON=/path/to/python3` задаёт интерпретатор при необходимости

## PowerShell

Скрипт использует `py -3` или `python` из PATH. В обоих скриптах переменная `PYTHON` позволяет явно выбрать интерпретатор;

Из корня проекта:

```powershell
.\e2e\run-e2e.ps1
```

Нужны .NET 10 SDK и Python 3.10+; сторонних Python-библиотек нет. Если сборка уже актуальна:

```powershell
.\e2e\run-e2e.ps1 -SkipBuild
```

Для проверки Docker-образа:

```powershell
.\e2e\run-e2e.ps1 -Docker
.\e2e\run-e2e.ps1 -Docker -SkipBuild
```

Docker-режим требует Docker Engine, локальный .NET не нужен. Используется Dockerfile в корне проекта. Каждый тест запускает отдельный контейнер на случайном порту с именем `vulnerability-tracker-e2e-<uuid>`. После теста контейнер останавливается и удаляется, его логи сохраняются. В обоих режимах выполняются одни и те же 25 сценариев;

Можно напрямую вызвать `python3 e2e/e2e.py --docker-image YOUR_IMAGE` для проверки другого заранее собранного образа с тем же API и портом 8080.

Каждый тест поднимает отдельный настоящий API на свободном loopback-порту, со своей SQLite in-memory БД и штатным сканером.Процесс останавливается и при ошибке теста; stdout/stderr сохраняются в `logs/local/<имя теста>.log` или `logs/docker/<имя теста>.log`. Ненулевой код выхода означает сбой.

25 сценариев с параметризованными проверками покрывают:

- Создание и чтение уязвимостей, все severity, границы названия, Unicode, обрезку пробелов, GUID v7 и серверное время.
- Разные записи для одинаковых запросов; параллельное создание и чтение.
- Неполные и некорректные DTO, числовые enum, невалидные URL, испорченный JSON, null/пустое тело, неверный Content-Type, неизвестные ID/маршруты и запрещённые методы.
- ProblemDetails, traceId, Location, Retry-After, OpenAPI с описаниями операций; работу API после ошибок валидации.
- Завершение сканирования пустого каталога; выбор существующих уязвимостей непрерывным фрагментом; вложенные DTO, случайные файлы и корректные диапазоны строк.
- Видимость новых уязвимостей и неизменность ранее сохранённого результата.
- Независимые задачи на повторные запросы; смешанную конкурентную нагрузку создания, чтения, сканирования и отмены.
- Лимит работников и ёмкость очереди, конкурентное переполнение, восстановление ёмкости, отмену Queued/Running, повторную отмену и освобождение работника.
- Единственного победителя конкурентной отмены; гонку отмены с завершением; устойчивость конечного состояния.
- Нормализацию URL и лимит 2048 символов до/после экранирования Unicode; проверку длины названия после обрезки пробелов.
- Отсутствие утечки ёмкости очереди после невалидных запросов, многократное освобождение работников отменой и конкурентную отмену уже завершённой задачи.
- Потерю данных после перезапуска процесса.
